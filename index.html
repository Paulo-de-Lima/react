01Iniciante

O que é React, afinal?

Uma biblioteca JavaScript para construir interfaces. Não um framework, não uma "linguagem" — uma forma de pensar a UI.

React foi criado no Facebook em 2011 e aberto ao público em 2013. Hoje é mantido pela Meta e por uma comunidade enorme. A ideia que o mantém de pé até hoje é quase poética:

A ideia central UI = f(state) A interface é uma função do estado. Mude o estado → a interface se atualiza.

Em vez de dizer ao navegador "encontre esse elemento, mude o texto dele, adicione uma classe", você descreve o resultado desejado e o React cuida do caminho. Isso é ser declarativo.

Imperativo 
// "como" fazer
const btn = document.querySelector('.btn');
btn.textContent = 'Salvo!';
btn.classList.add('success');

Você dirige cada passo e guarda o estado na cabeça.

Declarativo 
function Botao({ salvo }) {
  return <button className={salvo ? 'success' : ''}>
    {salvo ? 'Salvo!' : 'Salvar'}
  </button>;
}

Você descreve o estado atual. O React sincroniza o DOM.

✦
Aprendeu uma vez, usa em vários lugares. O mesmo modelo de componentes serve para web (React DOM), mobile (React Native), PDF, VR e até terminais (Ink).
02Iniciante

Por que React?

Não é sobre ser "o melhor". É sobre um conjunto de decisões de design que resolvem problemas recorrentes de interface.

◧

Componentização

UI dividida em pedaços independentes, reutilizáveis e testáveis. Você monta interfaces como quem monta com blocos.

⇄

Fluxo previsível

Dados descem via props, eventos sobem via callbacks. Um caminho claro reduce bugs em aplicações grandes.

⚡

Atualizações eficientes

O React compara a árvore e aplica só o que mudou. Você escreve código simples e ainda ganha performance.

◎

Ecossistema vasto

Roteamento, estado, dados, testes, SSR: praticamente qualquer necessidade já tem uma solução consolidada.

Outro ponto forte: o React DevTools. Ele permite inspecionar a árvore de componentes, ver props/state em tempo real e gravar perfis de renderização. Aprender a usá-lo cedo muda a forma como você depura.

i
Contexto importa. Para uma página estática simples, HTML + CSS já bastam. React brilha quando há estado, interação e muita reutilização.
03Iniciante

JSX: marcação dentro do JavaScript

Parece HTML, mas é JavaScript. Entender essa diferença evita 90% das dúvidas iniciais.

JSX é uma extensão de sintaxe que é transformada em chamadas React.createElement (ou jsx(), nas versões recentes) por um compilador como Babel, SWC ou esbuild. Nada de mágica em runtime.

As regras que valem lembrar

  • Expressões entre chaves: {variavel}, cálculos, funções — qualquer expressão JS válida.
  • className e htmlFor: porque class e for são palavras reservadas em JavaScript.
  • camelCase nos atributos: onClick, strokeWidth, tabIndex.
  • Um elemento raiz: use <>...</> (Fragment) quando não quiser criar uma <div> extra.
  • Chaves dinâmicas: style={{ color: 'red' }} — o primeiro par de chaves é JS, o segundo é o objeto.
✦
JSX não é obrigatório. É possível escrever React.createElement(...) à mão. JSX existe para tornar a estrutura visual legível — e a maioria dos projetos o usa.
04Iniciante

Componentes e props

A unidade básica do React: uma função que recebe entradas e devolve o que deve aparecer na tela.

Um componente é uma função JavaScript que aceita props (propriedades) e retorna JSX. Props são arguments — nada mais. Vêm de fora e são somente leitura.

Note os detalhes: children permite compor conteúdo arbitrário; valores padrão (tom = 'neutro') deixam a API amigável; e acao pode receber um botão inteiro — props transportam elementos, não só strings.

!
Nunca mut props. props.total = 10 é erro. Se precisa de algo derivado, crie uma variável local ou use estado. Componentes puros sempre retornam o mesmo resultado para as mesmas entradas.

Composição é o mecanismo favorito do React para reutilização. Em vez de criar hierarquias de herança, você encapsula partes e as encaixa. É o mesmo espírito de children — e ele reaparece em padrões avançados mais adiante.

05Iniciante

Estado: quando a tela precisa mudar

Props são entradas. Estado é a memória do componente — o que ele "lembra" entre renderizações.

O hook useState devolve um par: o valor atual e uma função para atualizá-lo. Ao chamar essa função, você pede ao React uma nova renderização com o novo valor.

Três leis do estado:

  1. Trate-o como imutável. Para arrays e objetos, crie uma cópia: setItens([...itens, novo]), setUser({ ...user, nome }).
  2. Use a forma funcional quando o novo valor depende do anterior — evita valores obsoletos em atualizações agrupadas (batching).
  3. O estado é local. Se dois componentes precisam do mesmo dado, eleve o estado ao ancestral comum — ou use contexto/estado externo (capítulos 09 e 12).
✦
Nem tudo deve ser estado. Se um valor pode ser calculado a partir de props ou estado existente, calcule-o durante a renderização. Menos estado = menos sincronização = menos bugs.
06Intermediário

Renderização: o que acontece após setState

Aqui começa a virada. Entender o ciclo separa quem "usa React" de quem domina React.

Quando o estado muda, o React executa uma renderização: chama seus componentes novamente, obtém um novo JSX e compara com a árvore anterior. Só as diferenças são aplicadas ao DOM real (commit).

1
TriggerEstado ou props mudam
2
RenderComponentes são chamados, JSX é calculado
3
ReconciliationÁrvore nova é comparada com a anterior
4
CommitDOM é atualizado; efeitos rodam

Essa comparação é o chamado Virtual DOM. A implementação atual do React usa o Fiber, uma estrutura que permite pausar, priorizar e retomar trabalho — base para os recursos concurrentes que veremos mais adiante.

Por que key importa tanto

Ao renderizar listas, a key diz ao React qual item é qual. Sem ela (ou usando o índice), uma reordenação pode preservar estado do item errado — campo de texto com valor trocado é o sintoma clássico.

Frágil 
{itens.map((item, i) => (
  <Item key={i} item={item} />
))}

O índice muda quando a lista é reordenada.

Estável 
{itens.map((item) => (
  <Item key={item.id} item={item} />
))}

IDs estáveis identificam cada elemento de verdade.

i
"Renderizar" não é "atualizar o DOM". Um componente pode renderizar e não gerar nenhuma mudança visível. Renderizações extras são normais, baratas e, na maioria dos casos, não precisam ser otimizadas.
07Intermediário

Efeitos: sincronizando com o mundo externo

useEffect é uma saída de emergência do React puro — para tudo que vive fora da renderização.

Renderização deve ser pura. Buscar dados, assinar eventos, iniciar timers ou manipular o DOM diretamente são efeitos colaterais — e o lugar para eles é useEffect.

O array de dependências

  • [] → executa uma vez na montagem (e limpa na desmontagem).
  • [id] → executa na montagem e sempre que id mudar.
  • Sem array → executa após toda renderização. Use com parcimônia.

A função de limpeza (return () => ...) evita vazamentos: cancela requisições, remove listeners, limpa timers. Em modo de desenvolvimento com StrictMode, o React monta → desmonta → monta de propósito para revelar efeitos sem cleanup.

!
Nem todo cálculo precisa de efeito. Filtrar uma lista ou derivar um valor deve acontecer durante a renderização. Use efeito apenas para sincronizar com algo externo ao React. As regras do useEffect são um dos temas mais importantes do guia oficial — vale ler.
08Intermediário

Hooks: reutilizando lógica com estado

Hooks são funções que "ligam" um componente aos recursos do React. Eles possibilitam extrair lógica repetida para fora da UI.

As duas regras sagradas: chame hooks apenas no nível superior (não dentro de condições, loops ou funções aninhadas) e apenas em componentes ou outros hooks. O React conta a ordem das chamadas para associar cada estado à sua posição — quebrar a ordem quebra tudo.

useReducerEstado com transições complexasMúltiplas ações relacionadas

useLayoutEffectEfeito antes da pinturaMedir elemento, evitar flicker

Hooks customizados

Quando uma lógica com estado se repete, extraia-a. O nome começa com use e o resultado é uma API limpa, desacoplada da interface.

✦
Use um linter. eslint-plugin-react-hooks detecta violações das regras automaticamente — inclusive dependências faltando em efeitos. É o melhor investimento de 5 minutos nesse tema.
09Intermediário

Contexto: dados sem "prop drilling"

Quando vários componentes distantes precisam do mesmo valor, passar props de mão em mão fica insuportável.

Prop drilling é o ato de atravessar props por componentes que não as usam só para chegar a um neto. O Context API resolve isso com um "canal" de dados: um Provider no topo e consumidores onde precisar.

Atenção: todo consumidor re-renderiza quando o value do Provider muda. Por isso, evite objetos grandes e instáveis — memoize o valor (useMemo) e separe contextos por domínio (tema, sessão, idioma) em vez de criar um "contexto Deus".

i
Contexto ≠ gerenciador de estado. Ele é um mecanismo de distribuição. Para estado complexo e de alta frequência, bibliotecas como Zustand, Jotai ou Redux oferecem seletores que evitam re-renderizações em cascata.
10Intermediário

Formulários: controlados ou não?

A forma mais comum de interação — e um dos lugares onde o modelo mental do React mais difere do HTML puro.

Em um input controlado, o valor vem do estado e o onChange o atualiza. O React é a fonte da verdade. Em um não controlado, o DOM guarda o valor e você o lê quando precisar (via ref ou FormData).

Formulários controlados são ótimos para validação em tempo real e dependências entre campos. Já em formulários grandes, digitar caractere por caractere provoca uma renderização por tecla — nesses casos, bibliotecas como React Hook Form (que usam refs e assinaturas) costumam ser melhores que manter 30 useState.

✦
Acessibilidade é parte do formulário. Sempre associe <label> ao input via htmlFor/id, use aria-describedby para mensagens de erro e aria-invalid para campos inválidos.
11Avançado

Performance sem adivinhação

Memoizar tudo é uma forma cara de não resolver nada. Meça primeiro, otimize depois.

Comece pelo React Profiler (DevTools → Profiler) e pelo React.Profiler em produção. Eles mostram quais componentes renderizaram, quanto tempo levaram e por quê. Com dados em mãos, escolha a ferramenta certa:

01

React.memo

Evita re-renderizar um componente se as props não mudaram. Útil em filhos "caros" com props estáveis.

02

useMemo / useCallback

Estabilizam referências para que memo funcione e evitam recomputar valores pesados.

03

lazy + Suspense

Divide o bundle: carrega rotas e recursos pesados só quando necessário.

04

Virtualização

Para listas com milhares de itens, renderize apenas o que está visível (react-window, TanStack Virtual).

!
Memoização tem custo. Cada useMemo/useCallback adiciona comparação e complexidade mental. Use quando há evidência de problema — não por reflexo. Regras mais baratas: stable keys, evitar objetos inline em props e manter componentes pequenos.
12Avançado

Padrões e arquitetura

Aqui o React deixa de ser "componentes" e passa a ser design de software.

Compound Components

Componentes que colaboram entre si e compartilham estado implícito via contexto. A API resultante é flexível e lê como HTML semântico.

Outros padrões do dia a dia

Render propsPassa uma função como prop para delegar o que renderizar. Base de bibliotecas como Downshift.
Container / PresentationalSepara "onde vem o dado" de "como aparece". Hoje é bastante substituído por hooks customizados, mas a ideia permanece.
PortalscreatePortal renderiza fora da árvore DOM — modais, tooltips e popovers sem problemas de z-index.
Error BoundariesComponentes de classe com getDerivedStateFromError que capturam erros de filhos e mostram um fallback.
Estados externosZustand/Redux para estado global; TanStack Query para dados de servidor (cache, revalidação, otimismo).

O que mudou nas versões recentes

React 18 trouxe Concurrent Rendering, useTransition, useDeferredValue e Streaming SSR. React 19 consolidou Actions, useActionState, use(), <form action> e metadados embutidos. O React Compiler automatiza memoizações que antes você fazia à mão.

i
Server Components (Next.js App Router, Remix) executam componentes no servidor e enviam menos JavaScript ao cliente. É um modelo mental novo: nem todo componente precisa "viver" no browser.

Próximos passos

Você já tem o mapa. Agora é construir — e usar as ferramentas certas para não travar.

Checklist mental antes de finalizar

  • ✓ Componentes pequenos, com responsabilidade clara e nomes descritivos.
  • ✓ key estável em listas; nada de índice em listas mutáveis.
  • ✓ Efeitos com cleanup e dependências corretas.
  • ✓ Tipagem com TypeScript para props e estado.
  • ✓ Testes com Vitest + Testing Library focados em comportamento.
  • ✓ Acessibilidade: labels, foco, contraste, navegação por teclado.
  • ✓ Mediu antes de otimizar; documentou decisões não óbvias.

01 Iniciante

Contador de Hábitos

~1h

Uma interface enxuta para acompanhar pequenos hábitos diários. O "olá, mundo" que já ensina a pensar em componentes.

ComponentesPropsuseStateKeys

O que construir

  • Componente Habito que recebe nome e contador por props.
  • Botão +1 que atualiza o estado no componente pai.
  • Lista com key estável e mensagem para lista vazia.
  • Botão "Reiniciar dia" que zera todos os contadores.

Desafio extra

Persista os contadores no localStorage criando um hook usePersistentState. Aqui você já usa o capítulo 08.

02 Iniciante → Intermediário

Lista de Tarefas com Filtros

~2h

O clássico todo list, mas com filtros, contadores derivados e histórico. Ótimo para treinar imutabilidade de estado.

FormuláriosEstado derivadoImutabilidadeuseReducer

O que construir

  • Input controlado com onChange para adicionar tarefas.
  • Filtros Todos / Ativos / Concluídos calculados na renderização.
  • Marcar e remover itens sem mutar o array original.
  • Contador de pendentes derivado — sem criar um segundo estado.

Desafio extra

Implemente "Desfazer" com useReducer guardando um histórico de estados. Teste a diferença entre estado e valor derivado.

03 Intermediário

Buscador de Repositórios

~3h

Uma busca em tempo real na API do GitHub. Aqui o React precisa conversar com o mundo — e lidar com latência e erro.

useEffectAbortControlleruseMemouseDeferredValue

O que construir

  • Busca com debounce e estados de carregamento, vazio e erro.
  • Cancelamento da requisição anterior no cleanup do efeito.
  • Ordenação dos resultados memorizada com useMemo.
  • Interface acessível: aria-live para os resultados.

Desafio extra

Troque o debounce manual por useDeferredValue e compare a sensação de uso. Depois meça com o Profiler.
